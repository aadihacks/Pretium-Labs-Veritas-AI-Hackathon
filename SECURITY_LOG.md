# Security findings, fixes, and decisions

This is Pretium Labs' shared security history. Human developers and coding agents must keep it current under [AGENTS.md](AGENTS.md#security-change-record-required). It records what went wrong, how someone could exploit it, what we changed, why we chose that approach, and what remains unverified.

Initial backfill: **November 5, 2026**, from available repository history, saved investigation records, and relevant chats, checked against the current `Beta-1.1-Editing` sources at base commit `2b12dc3`. The checkout also contains substantial uncommitted and concurrent work. This is an evidence-backed backfill, not proof that every earlier conversation or historical issue has been recovered. New discoveries and missing history belong here too.

## Reading the statuses

- **Implemented locally:** protection exists in the inspected checkout. It may still be uncommitted or undeployed.
- **Historical verification:** a prior investigation reports the stated checks. Those tests were not rerun for this documentation task.
- **Mitigated / open:** a particular attack path was reduced; the underlying issue remains possible.
- **Proposed / in progress:** a decision, request, or prototype exists; a finished production protection is not established.
- **Deployment unverified:** do not assume local source matches Render or the live database. A database function installation does not deploy the app.
- **Workbench status:** the security plugin's finding/patch record, tracked separately from source and runtime behavior. Failed patch generation does not establish that a local fix is absent or that a vulnerability is resolved.

An **API request** is a message sent directly to a server endpoint. A **Bearer token** proves possession of a login session. A **transaction** commits related database changes together or rolls them back together. **Idempotency** means repeating the same action cannot pay or spend twice. **RLS** means database row-level security, which works alongside grants restricting access to tables/functions. A **quota** is a limit on resource use; a rate limit restricts recent traffic, while a retained-storage limit restricts data that remains saved.

**Rationale provenance:** explicit user decisions and historical explanations are identified where available. Other "Why" statements in this backfill are maintainer analysis of the design and tradeoffs, not evidence of an unrecorded original discussion. Future updates should label that distinction within the entry when adding new reasoning.

## Detailed records

### SEC-001 — Shared admin account and password bypass

- **History/status:** committed removal in `9e14f9c` on October 24, 2026; current source uses Supabase Auth. Current deployed revision is unverified here.
- **Problem and exploitation:** the prototype exposed a shared `usercode` login and account-edit shortcut. Knowing the special identifier could bypass normal individual password verification and share an identity across users.
- **Solution and rationale:** remove the shared-admin login route and authenticate real accounts with Supabase. Account edits use real password verification. Removing the bypass closes the alternate trust path; hiding its button would leave direct requests possible.
- **Evidence:** [server.py](server.py), [script.js](script.js), [Auth documentation](supabase/AUTH.md), commit `9e14f9c` and its diff. Older tests that expect `ADMIN_ACCOUNT_STORE` or shared-admin behavior are obsolete; do not restore the shortcut to satisfy them.
- **Residual/verification:** the removal is supported by Git and current source; no hosted login attempt was made for this backfill.

### SEC-002 — “Fake API requests” and forged account ownership

- **History/status:** current boundary reviewed in **Audit browser data and API abuse**, November 5, 2026; the audit changed no application code. Controls are present locally; live policies/hosting were not inspected.
- **Problem and exploitation:** users control their browser and can bypass buttons, edit JSON, or send requests with a command-line client. A signed-in attacker can use their own valid token while inventing `owner`, `correct`, `xp`, `price`, or other fields. Browser validation, CORS, Origin checks, and public API-key visibility cannot establish that an action is legitimate.
- **Solution:** [history_api.py](history_api.py) verifies the Bearer token with Supabase and derives `user:<uuid>` from the verified identity. Domain handlers enforce ownership, valid server assignments, input shapes, state transitions, and limits. [account_data_api.py](account_data_api.py) follows the same authenticated-owner boundary. Missing, invalid, or anonymous member identity fails closed. Same-origin JSON checks provide an additional browser cross-origin defense.
- **Why:** put authority at the server where every request is checked. Client checks help users enter valid data but can be bypassed. Owning one account does not grant access to someone else's rows, arbitrary rewards, or arbitrary portfolio values.
- **Examples and evidence:** invented history sent to `/api/progress/import` is rejected with **410**; a made-up puzzle cannot become a graded result; forged account/price fields cannot select another owner or an execution price. See [history-import tests](tests/test_history_import_disabled.py), [history tests](tests/test_result_history.py), [account-data tests](tests/test_account_data.py), and [Competitive tests](tests/test_competitive.py).
- **Historical verification:** the referenced audit reported 98 Python boundary tests, 58 client tests, syntax checks, and localhost probes returning 401 for missing/forged sessions and 403 for cross-origin mutations. This is recorded evidence, not a new test run.
- **Residual:** an attacker with a stolen valid token can act within that user's permissions. A legitimate token also permits legitimate self-authored notes/settings. It does not make arbitrary claims trusted. See SEC-029 for browser privacy and SEC-031 for hosted checks.

### SEC-003 — Browser-controlled progression, wallet, and spending

- **History/status:** October 25 security release, commits `63c6b6e` and `6e2ff86`, PR #9. Historical live verification established that release used Supabase account storage. Later local changes require their own deployment verification.
- **Problem and exploitation:** editing browser XP/coin totals, submitting invented progression, skipping Ranked fees, or controlling payouts could yield extreme ranks and balances without earning them.
- **Solution:** authenticated server ledger for XP/coins, starter/reward claims, Ranked entry fees/stakes/payouts/refunds, and nickname spending. Balance checks and related writes are atomic; local/imported totals do not establish trusted progression. Durable private PostgreSQL storage replaces reliance on ephemeral hosting files for signed-in rewards.
- **Why:** a server-owned ledger validates the event that earns/spends value and survives browser changes/reloads. Encrypting or renaming localStorage would leave the user in control of the client.
- **Evidence:** [reward_wallet.py](reward_wallet.py), [account_database.py](account_database.py), [wallet tests](tests/test_reward_wallet.py), [coin client tests](tests/coin-rewards.test.cjs). Historical release evidence reported 83 Python tests, 93 JavaScript tests, 16 PostgreSQL security cases, independent-process persistence, browser-role access denial, and a legitimate starter claim surviving reload.
- **Residual:** legitimate rewarded gameplay can still be farmed if its answer is recoverable (SEC-011). Server-calculated rewards alone do not solve answer disclosure.

Guest rotation/practice admission is persistent and bounded. All three reproductions have regression coverage. ### SEC-004 — Forged grades, duplicate submissions, and Review reward replay

- **History/status:** server history/reward architecture introduced in October 2026 and present locally. Individual deployment status beyond SEC-003 is unverified here.
- **Problem and exploitation:** claim a correct answer or reward in JSON; send concurrent copies of one result; retry after a lost response; edit a result's chart; use Review hints or early checks while still claiming full reward.
- **Solution:** grade stored server snapshots, freeze the first committed choice, bind snapshots to owner/mode, and save results/rewards together. Review uses server timing and persisted eligibility, keeps the original result, and pays eligible retries once. Hints/manual early checks forfeit the associated Review XP eligibility.
- **Why:** atomicity and unique reward sources stop racing requests and accidental retries from minting extra value while allowing recovery after network failures.
- **Evidence:** [result_history.py](result_history.py), [reward_wallet.py](reward_wallet.py), [history tests](tests/test_result_history.py), [Review reward tests](tests/review-rewards.test.cjs), [retry tests](tests/review-retry-status.test.cjs). Existing tests cover forged outcome fields, concurrent submissions, rollback, wrong Review answers, and hint forfeiture; they were not rerun for this backfill.
- **Residual:** a correctly submitted answer obtained by historical lookup is a separate flaw (SEC-011).

### SEC-005 — Ranked prediction after a candle has started

- **History/status:** implemented October 25–27; local contract `live-v2` is present. No deployment was performed by that fix task.
- **Problem and exploitation:** predict after some of the target candle's price movement is already visible, or forge client timestamps/stakes to enter late with advance knowledge.
- **Solution:** new rounds target a complete future candle. Entry, stake changes, and direction submissions close five seconds before `targetStart`, according to server time. Direction and confirmed stake freeze together. Score the target candle's own open-to-close move. Reject new legacy wagers while settling previously accepted legacy rounds by their original rules.
- **Why:** move the commitment before any outcome movement is visible and enforce the same rule on direct API/wallet paths. Preserve accepted contracts instead of retroactively changing their scoring.
- **Evidence/verification:** [ranked_rules.py](ranked_rules.py), [result_history.py](result_history.py), [reward_wallet.py](reward_wallet.py), [Live tests](tests/test_live_puzzles.py), [wallet tests](tests/test_reward_wallet.py). Historical checks: 89 Python and 69 JavaScript tests, served-file matching, and Chrome checks from 320 to 1920px. Hosted PostgreSQL mutations and other browsers were not exercised in that fix.
- **Residual:** unanswered/unscorable rounds may refund; submitted/revealed bets cannot be undone with a forged refund request.

### SEC-006 — Equivalent crypto symbols paid as separate Ranked rounds

- **History/status:** October 29 local patch; source present, hosted behavior unverified. Scan `f9988e81` remained failed/incomplete.
- **Problem and exploitation:** spell one provider asset with different separators/aliases and make the same account/target appear to be distinct entries, submissions, or progression rewards.
- **Solution:** canonical provider asset identity plus legacy-alias matching at issuance, payment, submission, and reward boundaries. Keep genuinely different assets, accounts, intervals, and targets separate. Settle accepted old wagers without duplicate progression rewards.
- **Why:** uniqueness must follow the market identity rather than the user's spelling. A UI-only normalization would leave direct requests and old records inconsistent.
- **Evidence/verification:** [ranked_rules.py](ranked_rules.py), [server.py](server.py), [result_history.py](result_history.py), [reward_wallet.py](reward_wallet.py), [alias tests](tests/test_ranked_aliases.py). Historical report: 126 Python and 68 JavaScript tests, including concurrency and forged-refund boundaries.
- **Residual:** the scan also reported sensitive private configuration copies; those were not rotated or removed by this patch (SEC-026).

### SEC-007 — Future predictions crowding due settlement out of the queue

- **History/status:** October 28–29 local fix, also represented in `2b12dc3`; deployment unverified.
- **Problem and exploitation:** the queue selected the oldest 100 pending rows before excluding targets that had not ended. Enough long-lived predictions could hide other users' due results and delay settlement.
- **Solution:** filter numeric `targetEnd <= server time` before applying the batch limit; interleave owners and prioritize their earliest due work. Preserve accepted attempts, refunds, and idempotency.
- **Why:** select eligible work at the database boundary and prevent one owner's backlog from dominating. Raising the batch size would only move the attack threshold.
- **Evidence:** [ResultStore.pending_live](result_history.py), [queue regression tests](tests/test_ranked_settlement_queue.py). The combined historical settlement/visibility patch reported 158 Python and 79 JavaScript tests; those totals cover more than this one fix.
- **Residual:** selection fairness does not by itself prove the worker handles every unexpected exception (SEC-008).

### SEC-008 — Players assigning server-managed Competitive puzzles

- **History/status:** original audit confirmed a high-impact assignment/worker disruption path; later local source blocks it. Generic worker resilience remains a separate follow-up.
- **Problem and exploitation:** a match member could use a generic history endpoint to assign a different puzzle to a future Competitive round. Conflicting round data could fail settlement and escape the shared processing loop, affecting other matches or Ranked work.
- **Solution:** only the Competitive server assigns current/future match puzzles. Generic history issuance rejects those assignments; players submit choices against their actual membership and round state.
- **Why:** membership permits playing a round, not replacing its challenge. Reject the unauthorized state change before it is stored.
- **Evidence:** [result_history.py](result_history.py), [competitive.py](competitive.py), [Competitive tests](tests/test_competitive.py), especially generic-endpoint bypass and current/future issuance cases. **Audit client API keys** explicitly distinguished original audit tests from later patch verification.
- **Residual:** the earlier audit noted an unexpected Competitive `DailyError` could still escape the outer settlement loop. This backfill did not verify that broader resilience issue as fixed or deployed.

### SEC-009 — One Competitive reveal exposing a later round's answer

- **History/status:** November 5 follow-up inspected existing local protection. Scan `e2c49cb9-b28e-4ace-8b32-e16fd6192204`; workbench findings remained open and generate requests failed to produce a new patch. Local implementation and plugin status differ.
- **Problem and exploitation:** five rounds could reuse historical candles. After round one revealed all 72 candles, some of those prices could be the 26 hidden answer candles of a later round. Recognizing the repeated stretch gives advance knowledge.
- **Solution:** select five disjoint 72-candle windows and independently reject overlapping provider batches before saving rounds. Retain normal reveals/scoring/rewards and existing accepted matches.
- **Why:** prevent disclosure through shared data selection. Masking dates or delaying a button would not remove the already revealed prices. Existing accepted matches were preserved rather than rewritten.
- **Evidence/verification:** [competitive.py](competitive.py), [Competitive tests](tests/test_competitive.py). November 5 chat reported 42 tests and 21 additional probes passing against existing local code.
- **Residual:** historical matching via other routes is still open (SEC-011); accepted pre-fix matches were not retroactively replaced. No hosted verification.

### SEC-010 — Hidden prediction endings sent to the browser too early

- **History/status:** October 27–28 mitigations for Free/Speed/Event predictions; implemented locally, portions committed in `2b12dc3`. Original scan `95a8fb1d` failed with partial coverage.
- **Problem and exploitation:** inspect a network response, JavaScript object, saved preview, or caller-selected known window to learn the ending before committing a rewarded prediction.
- **Solution:** keep full snapshots on the server; return only observed candles under an owner/mode-bound server-issued assignment; commit the first choice before revealing the ending. Preserve Speed deadlines on reload, prevent cross-mode reassignment, and give guest reveals no authoritative account rewards.
- **Why:** data already delivered to the browser cannot be kept secret by a cloud overlay or disabled controls. Conceal the outcome at the response boundary and validate issuance server-side.
- **Evidence:** [result_history.py](result_history.py), [server.py](server.py), [hidden prediction tests](tests/test_hidden_predictions.py), [practice-window tests](tests/test_practice_windows.py). The earlier combined mitigation report recorded 153 JavaScript and 117 backend tests.
- **Residual:** this closes direct preloading/assignment paths; access to matching public history can still reveal answers indirectly (SEC-011).

### SEC-011 — Recovering historical answers by matching chart patterns

- **History/status:** repeatedly identified October 25–November 5; **open, with partial mitigation**. November 5 follow-up reproduced recovery despite passing existing practice tests. Associated occurrence `occ_f1f917cf798b602f9a5353bd` in scan `e2c49cb9-b28e-4ace-8b32-e16fd6192204` remains open.
- **Problem and exploitation:** full historical candles returned by `/api/chart` and related saved/public data can be matched to the observed part of a concealed practice puzzle. Once the stretch is found, its later prices give the answer, allowing correctly graded but unfair XP/coin earnings. The attacker can use legitimate requests and their own account.
- **Mitigation:** [historical_visibility.py](historical_visibility.py) indexes visible prices to 100, replaces timestamps with ordinal slots, removes volume/provider clues, and conceals Daily/Competitive identity until reveal. Reject custom practice date windows and fake Event Pack aliases; vary newly generated Daily windows. Keep original snapshots for authoritative grading and later Review.
- **Why / decision:** the user chose real historical practice, existing rewards, and lookup friction; they did not authorize restricting historical chart access. Ordinary Paper Trading is not the cheating target. Masking reduces easy lookup but preserves relative patterns, so it cannot prove secrecy.
- **Evidence:** [visibility code](historical_visibility.py), [visibility tests](tests/test_historical_visibility.py), [hidden tests](tests/test_hidden_predictions.py), **Detect historical chart cheating**, **Continue security scan**, and the November 5 remediation follow-up. Prior isolated tests recovered a hidden answer and received server rewards; later tests again recovered answers.
- **Alternatives still needing product authorization:** change prediction data to generated data, use future-only outcomes, change rewards, or restrict full-history access. These were discussed, not implemented as a complete solution. An earlier acceptance of lookup risk does not close later findings automatically.
- **Residual:** raw chart matching, external history, saved Paper/Review data, pack dates, and prior results remain relevant. No anti-cheat detection or punishment was added by these mitigations.
